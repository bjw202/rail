# 작업자 지시서 쓰는 법

띄우기·닫기·기록은 `worker start`·`worker done` 이 Orca 에 부르고 남긴다(`log worker_*` 를 손으로 쓰지 않는다). 리더는 명세 `.orchestration/<step>-spec.md` 만 쓴다. 첫 `# ` 제목이 일 이름이 된다(`# M1-2 세션 목록` 꼴).

## 늘 넣을 것
- 처음 읽을 파일: `CLAUDE.md`, step 표의 그 줄, 고칠 파일.
- 할 일: 함수 이름과 입출력까지.
- 범위: 고쳐도 되는 파일(표 그대로). 밖을 고쳐야 하면 고치지 말고 `worker_done` 에 까닭을 적는다.
- 하지 말 것: 커밋(worktree 방식의 만드는 역할은 예외: `worker start` 가 명세 끝에 붙이는 "작업 폴더와 커밋" 절대로 자기 브랜치에 커밋), 실행 의존성 더하기, 포트 열기(리허설 밖), 구현 step 이면 시험 파일 고치기. 시험이 틀렸다고 보면 고치지 말고 까닭을 적는다.
- 완료 기준: 표 그대로, 돌릴 명령과 기대 결과.
- 보고: 고친 파일, 돌린 명령과 결과, 남은 문제.

## 맡는 쪽마다 더할 것
- 기능: 시험과 구현을 함께 쓴다. 완료 기준은 표 그대로, 실제 기록으로 본 숫자를 보고에 적게 한다.
- 확인: `.rail/check/template.md` 의 빈칸만 채운다. 만든 작업자의 대화·보고서 해석은 넣지 않는다.
- 고침: 확인의 must 목록과 재현 시험 경로를 그대로 넣는다. 재현 시험(`.rail/check/<step>/`)은 고치지 않는다.
- 시험(예전 방식): "`src/` 의 구현 코드를 열지 마라." 구현을 본 시험은 구현을 따라 쓴다.
- 리뷰·마지막 리뷰: "`.rail/review/calibration.md` 를 먼저 읽고 지적을 `.rail/review/<step>.json` 에 써라. 꼭 고칠 것(must)마다 재현 방법을 한 줄로 적어라."
- 마지막 리뷰(Codex): 그 마일스톤의 `git diff <첫 커밋의 부모>..HEAD --stat` 범위와 바뀐 파일 목록을 적고 "이 범위만 보라. 저장소 전체를 뒤지지 마라."라고 쓴다. 판정으로 고친 시험이 있으면 `status` 가 내는 목록을 넣고 "시험을 느슨하게 만들지 않았는지 보라"를 더한다.
- 낡은 시험 판정(`--role stale`, step `<step>-stale`): `.rail/check/stale-template.md` 의 빈칸만 채운다. 막힌 작업자의 까닭은 그대로 넣되 그 작업자에게 판정을 맡기지 않는다.
- 리허설: 구현하지 않은 새 세션이다. rail-check 의 "리허설 지시서에 넣을 것"을 더한다.

## 판단할 것
- 끝난 작업자에게 후속 일을 보내지 않는다. 고칠 것이 있으면 닫고 새 작업자를 띄운다.
- 작업자를 버리는 것(`worker done --force`)은 사람이 정했을 때만 한다.
- `RAIL_ALLOW_TEST_EDIT` 는 허락받은 step 의 작업자 하나에만 간다. `worker start` 가 그 step 의 다음 작업자 명령 앞에 붙이고, orca 로 직접 띄우지 않는다. 허락 없이는 시험 잠금 훅이 그대로 일해야 한다.
- 잠긴 시험을 고쳐야 할 때: `.rail/config.json` 의 `staleTests` 가 `agent` 면 사람에게 묻지 않고 판정 작업자 `<step>-stale` 을 띄운다. 끝나면 `worker done <step>-stale` 뒤 `worker start <step>` 이 stale 줄만 허락하고(명세 끝에 고쳐도 되는 줄을 붙인다) keep 줄은 거절한다. 판정 파일이 없거나 깨졌거나 한 마일스톤에 시험 파일 5개를 넘으면 허락하지 않으니, 그때와 `human` 설정일 때는 예전처럼 step 이름을 넣어 "M8-6 에서 시험 고치기를 허락할까요? (그 줄과 까닭)"라고 묻는다. 고친 목록은 마일스톤 끝 장면 질문이 사람에게 보인다.
